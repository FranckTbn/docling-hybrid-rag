# Architecture

`ingest_document` télécharge ou lit un PDF, vérifie son identité, appelle le pipeline Docling de l'article, construit ses parents/enfants et enregistre les vecteurs. `store.py` gère la base : `catalog.json` relie chaque PDF à son dossier, et le `manifest.json` du dossier enregistre les entrées et l'empreinte des fichiers de chaque étape (parsing, chunking, embeddings). Une étape est réutilisée si ses entrées n'ont pas changé et si ses fichiers sont intacts. Le catalogue ne marque un document `ready` qu'après toutes les étapes. Un échec laisse les étapes réussies réutilisables au prochain appel.

L'ingestion construit aussi BM25 (`indexing.py`) sur les enfants contextualisés de toute la base, avec racinisation française, et sauvegarde un index identifié par leur contenu. `load_knowledge_base` vérifie que les étapes de chaque document `ready` se suivent, puis rassemble ses parents, enfants et vecteurs et recharge cet index BM25. `hybrid_retrieval` classe les enfants avec BM25 (éventuellement après l'expansion de `expansion.py`) et avec le dense, ramène chaque canal à ses parents par le meilleur enfant, applique RRF, puis, si un reranker est fourni, relit le meilleur enfant de chaque parent candidat. `build_context` recharge uniquement les documents sélectionnés et prépare leur texte, leurs images et le registre des sources.

`create_workflow` expose le graphe compilé avec `InMemorySaver`. `remember` ajoute la question et remet à zéro les résultats du tour précédent. Le réducteur de `messages` conserve trois messages utilisateur/assistant au total. `thread_id` isole les conversations ; la mémoire et les anciens checkpoints restent dans le processus Python.

`route_question` appelle le LLM avec cet historique. `RouteDecision` borne la branche à `direct` ou `retrieve`, le budget documentaire à 3, 5 ou 7 parents et le découpage à 1 à 3 sous-questions ; il fournit aussi une question autonome pour les relances. `direct` appelle le LLM sans ouvrir la base. Pour `retrieve`, `prepare_search` charge la base et encode toutes les sous-questions en un lot, puis `Send` lance une branche `search_theme` par sous-question avec sa part du budget (`split_budget`). Une branche peut reformuler sa sous-question si le reranker la juge sous `relevance_threshold`. `merge` réunit les parents des thèmes sans doublon, `answer` rédige la réponse, puis `verify` ajoute au message l'alerte du contrôle de soutien (`verification.py`). Chaque branche ajoute seulement sa réponse finale à `messages` ; `themes` est remis à zéro à chaque tour.

`answer.py` conserve le prompt documentaire et la validation de l'article : le contexte courant fait preuve, pas les anciennes réponses. Les noms et les liens de citation sont construits par le code. La mémoire ne modifie ni le parsing ni l'indexation. Les dépendants de l'interface `invoke` sont le README, `demo.ipynb`, `tests/test_pipeline.py` et `tests/test_workflow.py` : tous doivent fournir un `thread_id`.

Les modules de présentation du notebook n'interviennent pas dans les scores. Un changement d'options, de code ou de version invalide l'étape concernée ; comme chaque étape enregistre l'empreinte du fichier de la précédente, les suivantes sont recalculées si ce fichier change. Les changements de contexte ou de prompt concernent la génération, pas les embeddings. Les sources ont une identité `(document_id, self_ref)` ; un renvoi Docling seul ne distingue pas deux PDF.
